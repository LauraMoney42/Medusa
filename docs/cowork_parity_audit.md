# Claude Code / Cowork Parity Audit

**Project:** Medusa
**Date:** 2026-09-15
**Workstream:** W1 (see `docs/2026-09-15_cowork_parity_tauri_agnostic_plan.md` Sections 4 and 9)
**Method:** official docs on `code.claude.com/docs`, the Cowork help articles on `support.claude.com`, the desktop pages, and the public `anthropics/claude-code` changelog, diffed against a grep-level survey of `client/src` and `server/src`. No binary was decompiled.

Priority key: **P0** blocks credible parity or is actively broken today. **P1** is visible parity a user will notice missing. **P2** is polish or a later-phase item.

**One clarification before the matrix.** "Cowork" and "Claude Code desktop" are two different tabs of the same desktop app. Cowork is the non-coding agentic surface (cloud sessions, Projects, artifacts, connectors, a built-in browser side panel, computer use, mobile dispatch). Code is the GUI over Claude Code (worktrees, diffs, terminal, panes). Medusa's shape, a local hub of long-lived named agents over a Node server, sits closer to the Code tab, so Code is the primary parity target and Cowork rows are marked as such.

## 2. UX flows

Each entry is **trigger -> what appears -> what the user can do next**, first for Claude Code / Cowork as documented, then for Medusa today.

### Session sidebar
- **Claude Code desktop.** `Cmd+N`, or clicking New session, opens a folder picker with an optional worktree toggle. A row appears in the sidebar grouped by project, with a live status dot and a diff stat. From there the user renames, archives, `Cmd+Click`s for a side-by-side view, filters by status or environment, or opens the Routines and Scheduled sections. (https://code.claude.com/docs/en/desktop)
- **Medusa.** `NewSessionButton.tsx` opens `SessionEditor.tsx`, which collects name, working dir, model, yolo toggle, system prompt, and skills. The row lands in `SessionList.tsx`. Next actions: open, rename, edit, delete. No archive, no worktree toggle, no grouping, no side-by-side.

### Chat and tool cards
- **Claude Code desktop.** Sending a prompt streams text token by token, then each tool call appears as its own card with a status spinner, then the result folds into the card. `Ctrl+O` cycles Normal / Verbose / Summary. File paths inside cards are clickable and open the editor pane; right-click offers "open in VS Code", "show in Finder", "copy path". (https://code.claude.com/docs/en/desktop)
- **Medusa.** `ChatInput.tsx` submits over Socket.IO; `MessageList.tsx` renders `MessageBubble.tsx` with `ToolUseBlock.tsx` children. In practice a whole assistant turn lands at once and tool cards are usually absent, because `handler.ts` reads only `text` blocks out of `assistant_complete` and never parses `type: "user"` tool results. Next actions: expand a card, abort the turn, scroll.

### Permission prompts
- **Claude Code.** A tool call that no rule covers pauses the turn and shows a prompt naming the tool and its input, with Yes / Yes and don't ask again / No. `Esc` equals No; `Tab` opens a comment field on Yes or No so the user can explain; a Bash prompt can also offer "Yes, and switch to auto mode". "Don't ask again" writes a rule into `.claude/settings.local.json`, at the main checkout root even from a worktree. Rules are evaluated deny, then ask, then allow, first match wins. In `-p`, a permission host (`--permission-prompt-tool` or the SDK `canUseTool` callback) answers instead, and `--permission-prompts none` denies everything that would otherwise prompt. A `PermissionRequest` hook can decide before any of this, and a `PermissionDenied` hook can set `retry: true`. (https://code.claude.com/docs/en/permission-modes, https://code.claude.com/docs/en/permissions, https://code.claude.com/docs/en/headless)
- **Medusa.** A bot must *voluntarily* emit `[HUB-POST: @You APPROVAL NEEDED: ...]`. `hub-detector` strips the marker, `ApprovalStore` records it, and `ApprovalBanner.tsx` shows an Approve / Deny card. Resolving posts `@Bot ✅ APPROVED: ...` back into the Hub as if the user typed it. Real tool-level permissions are either bypassed (`--dangerously-skip-permissions`) or unanswerable.

### Model picker
- **Claude Code desktop.** `Cmd+Shift+I` or the dropdown by the send button lists available models plus an effort control; switching applies mid-session. In the CLI, `/model` with no argument opens a picker showing each alias, the model it resolves to, an effort slider, per-1k prices, availability, and org defaults; `Enter` switches and saves as the default, `s` switches for this session only. Aliases include `default`, `opus`, `sonnet`, `haiku`, `fable`, `best`, `opusplan`, `sonnet[1m]`, `opus[1m]`. `--fallback-model sonnet,haiku` covers a failed turn. (https://code.claude.com/docs/en/desktop, https://code.claude.com/docs/en/model-config)
- **Medusa.** Model is a per-session field chosen in `SessionEditor.tsx` from four hardcoded Anthropic tiers, with an automatic tier router (`server/src/claude/model-router.ts`) that can override by prompt pattern. `ChatHeaderControls.tsx` switches provider between `claude` and `kimi` globally, not per session.

### Usage display
- **Claude Code desktop.** Clicking the usage ring beside the model picker shows this session's context-window fill and the plan usage shared across all Claude surfaces. In the CLI, `/usage` (alias `/cost`) prints total cost, API duration, wall duration, lines added and removed, a per-model table of input / output / cache-read / cache-write tokens with a dollar figure each, a prompt-cache hit-rate line, and plan usage bars with attribution by skill, subagent, plugin, and MCP server; `d` and `w` toggle 24 hours versus 7 days. `/insights` writes an HTML report over up to 200 recent sessions. Included limits reset every five hours. (https://code.claude.com/docs/en/costs)
- **Medusa.** `TokenRing.tsx` sits in the bottom toolbar; `UsagePane.tsx` shows total cost, message count, average cost, and a cost-by-bot table for day / week / month, sourced from `server/src/metrics/token-logger.ts`. No context-window gauge and no plan headroom.

### Browser pane
- **Claude Code desktop.** `Cmd+Shift+B` opens the pane on the dev server declared in `.claude/launch.json`; Claude drives it to verify its own edits, and an external site asks for approval once or always. (https://code.claude.com/docs/en/desktop)
- **Medusa.** `CoworkPane.tsx` subscribes to a CDP screencast from `server/src/cowork/screencast.ts`, which attaches to a Chrome the user launched with `--remote-debugging-port=9222`. The user can take over with mouse and keyboard, forwarded as `Input.dispatchMouseEvent` / `Input.dispatchKeyEvent`. The agent cannot drive it, and there is no launch config.

### Artifacts
- **Cowork.** Either ask inside a session, or open the Artifacts view in the Cowork sidebar and click "New artifact", at which point Claude asks setup questions about which connectors to pull from. The artifact opens as an interactive page (dashboard, tracker, reference, comparison tool). Edits auto-save and every update creates a new version the user can compare or restore. Sharing is by link, and a shared artifact runs on the *viewer's* connector access rather than the author's. (https://support.claude.com/en/articles/14729249-use-artifacts-in-claude-cowork)
- **Medusa.** Nothing. The nearest thing is writing an HTML file to disk and telling the user the path.

### Settings
- **Claude Code desktop.** Settings > Claude Code exposes local env vars, worktree location, browser data, auto-archive on PR merge, denied apps for computer use, and the default permission mode for new sessions. (https://code.claude.com/docs/en/desktop)
- **Medusa.** `SettingsModal.tsx` covers provider, TTS voice toggles, and OneNote linking; `server/src/settings/` persists `activeProvider` and Microsoft OAuth fields to `~/.claude-chat/settings.json`.

### Slash commands
- **Claude Code.** Typing `/` at the start of the prompt opens a menu of built-ins and user commands, with `!` for shell mode, `@` for file and session mentions, and `:` for emoji shortcodes on the same first keystroke. There are roughly 90 built-ins (`/model`, `/usage`, `/permissions`, `/hooks`, `/mcp`, `/agents`, `/skills`, `/memory`, `/rewind`, `/resume`, `/branch`, `/export`, `/diff`, `/plan`, `/loop`, `/desktop`, `/config`, `/status`, and more). User commands are `SKILL.md` folders under `~/.claude/skills/` or `.claude/skills/`, with frontmatter for `description`, `argument-hint`, `allowed-tools`, `model`, `context: fork`, and `paths`, plus `$ARGUMENTS` substitution and inline `` !`cmd` `` shell injection. A subset (`/model`, `/effort`, `/fast`, `/config key=value`) works in `-p`. (https://code.claude.com/docs/en/commands, https://code.claude.com/docs/en/slash-commands)
- **Medusa.** `/` is plain text. There is no command registry, palette, or expansion.

### Hooks
- **Claude Code.** A `settings.json` `hooks` block maps a lifecycle event, optionally narrowed by a `matcher` and an `if` permission-rule condition, to handlers of type `command`, `http`, `mcp_tool`, `prompt`, or `agent`. The harness executes them, not the model, so they are deterministic: exit 0 succeeds and its stdout JSON decides the outcome, exit 2 blocks the action outright, and anything else is a non-blocking error. Every hook receives `session_id`, `transcript_path`, `cwd`, `permission_mode`, `effort.level`, and the event name on stdin, and can return `hookSpecificOutput.additionalContext` to inject into the conversation. `/hooks` shows what is configured. `SessionStart` and `Setup` hooks stream `hook_started` / `hook_progress` / `hook_response` events before `system/init`. (https://code.claude.com/docs/en/hooks)
- **Medusa.** None. Automations are expressed as prompt text inside a bot's system prompt, which is unreliable by construction.

### MCP
- **Claude Code.** `claude mcp add` or a `.mcp.json` at the repo root declares `http`, `sse`, `stdio`, or `ws` servers in one of three scopes (local, project, user), with `${VAR:-default}` expansion in commands, args, env, urls, and headers. `/mcp` opens a panel showing per-server health (Connected, Needs authentication, Failed to connect, Pending approval, Disabled for this project), tool counts, OAuth sign-in, reconnect, and per-project enable/disable. Server resources are `@`-mentionable and server prompts appear as `/server:prompt`. `system/init` lists `mcp_servers` with status and `mcp_server_errors` for entries skipped by validation. (https://code.claude.com/docs/en/mcp)
- **Medusa.** None. Whatever MCP servers the user's own `~/.claude` config provides are inherited invisibly by the spawned CLI, and Medusa discards the `mcp_servers` field it already receives.

### Skills
- **Claude Code.** A `SKILL.md` with `name` and `description` frontmatter is discovered from `~/.claude/skills`, `.claude/skills`, a nested `<subdir>/.claude/skills` in a monorepo, or a plugin (as `/plugin:skill`). Claude invokes it by description match, or the user types `/skill-name`. Frontmatter controls `allowed-tools` (pre-approved for that turn only), `context: fork` with `agent:` and `background:` to run it in a subagent, `paths` globs to gate auto-loading, `arguments`, and `hooks`. `skillOverrides` in settings can set a skill to `on`, `name-only`, `user-invocable-only`, or `off`. Content stays in context across turns; on auto-compaction a re-invoked skill keeps its first 5,000 tokens. (https://code.claude.com/docs/en/skills)
- **Medusa.** `SkillPicker.tsx` browses a remote GitHub catalog via `server/src/skills/catalog.ts` and stores selected slugs on `SessionMeta.skills`, which are folded into the system prompt. There is no local skill directory, no `/skill-name`, and no Skill tool.

### Subagents
- **Claude Code.** Claude calls the `Agent` tool (listed as `Task` in the `system:init` tool list). A subagent is a markdown file in `.claude/agents/` or `~/.claude/agents/` whose frontmatter sets `name`, `description`, `tools`, `disallowedTools`, `model`, `permissionMode`, `maxTurns`, `skills`, `mcpServers`, `hooks`, `memory`, `background`, `effort`, and `isolation: worktree`. It starts with no parent conversation, only its system prompt and the Agent tool's prompt string, and returns only its final message. Built-ins are `Explore`, `Plan`, and `general-purpose`. Nesting is capped at 3 layers and 20 concurrent by default. `/agents` manages them, the desktop Subagent and Tasks panes list them live, and their messages arrive in the stream with `parent_tool_use_id` set. (https://code.claude.com/docs/en/sub-agents, https://code.claude.com/docs/en/agent-sdk/subagents)
- **Medusa.** No in-session subagents. Parallelism is modelled as separate long-lived bot sessions coordinated through the Hub with `@mentions` and `[BOT-TASK: ...]` markers.

### Scheduled tasks / routines
- **Claude Code desktop.** Routines > New routine > Local, with name, description, instructions (plus permission-mode and model pickers), folder, worktree toggle, and a schedule preset. On fire: a desktop notification plus a new session under a **Scheduled** sidebar section. The detail page offers Run now, Active/Paused, Edit, run history with skip reasons, an "Always allowed" panel, and Delete. Missed runs get one catch-up. (https://code.claude.com/docs/en/desktop-scheduled-tasks)
- **Three-way split worth copying.** Claude Code offers cloud **Routines** (run without your machine, minimum interval 1 hour, triggerable by API call or GitHub event), **desktop scheduled tasks** (local files, minimum 1 minute, machine must be awake), and **`/loop`** (session-scoped, needs an open session). Medusa's runner protocol makes the first tier plausible later; the middle tier is the one to build now. (https://code.claude.com/docs/en/routines, https://code.claude.com/docs/en/scheduled-tasks)
- **Medusa.** `poll-scheduler.ts` runs on a timer when `HUB_POLLING=true`, picks up to four idle bots per tick with a two-minute per-bot cooldown, and sends them a `[Hub Check]` prompt. There is no user-facing routine, no schedule UI, and no run history.

### Memory
- **Claude Code.** `CLAUDE.md` at user, project, and local scope is loaded at session start; `--bare` skips discovery; subagents can opt out with `omitClaudeMd`. (https://code.claude.com/docs/en/memory)
- **Medusa.** A per-session `systemPrompt` (plus a shorter `compactSystemPrompt` for polls) stored in `sessions.json`. Because the spawned CLI still runs in `workingDir`, a project `CLAUDE.md` is loaded by the CLI itself, invisibly, with no Medusa UI over it.

### Plan mode
- **Claude Code.** `Shift+Tab` to `⏸ plan mode on`, or `claude --permission-mode plan`, or prefix one prompt with `/plan`. Claude reads and explores but does not edit. When it finishes, an approval dialog offers "Yes, and use auto mode" (or auto-accept edits, or switch to bypass), "Yes, manually approve edits", and "No, keep planning"; `Ctrl+G` opens the proposed plan in the editor first. Accepting a plan also generates a session title. (https://code.claude.com/docs/en/permission-modes)
- **Medusa.** Nothing. The nearest analogue is asking a bot to write a spec into `docs/`.

### Worktrees
- **Claude Code.** `--worktree <name>` or the desktop toggle creates `.claude/worktrees/<name>` on branch `worktree-<name>` from the default branch, copies files matched by `.worktreeinclude`, and blocks edits and git redirects that reach the main checkout. On exit, a clean worktree is removed automatically and a dirty one prompts keep-or-remove. (https://code.claude.com/docs/en/worktrees)
- **Medusa.** No worktree concept; concurrent bots in the same `workingDir` can and do collide.

## 3. stream-json contract

What `claude -p --output-format stream-json --verbose [--include-partial-messages]` emits, versus what Medusa parses in `server/src/claude/stream-parser.ts` and `server/src/claude/types.ts`, and what appears in `docs/stream-format-example.jsonl` (75 lines: 3 `system/init`, 8 `stream_event`, 4 `assistant`, 1 `user`, 3 `result/success`).

| Event | Key fields | Description | Medusa |
|---|---|---|---|
| `system` / `init` | `session_id`, `cwd`, `model`, `tools[]`, `mcp_servers[]`, `mcp_server_errors[]`, `permissionMode`, `apiKeySource`, `claude_code_version`, `plugins[]`, `plugin_errors[]`, `capabilities[]`, `uuid` | First event of the run (unless startup hook or plugin events precede it). Session metadata. | **Partial.** `SystemInit` declares only `session_id`, `cwd`, `model`, `tools`. `mcp_servers`, `permissionMode`, `apiKeySource`, `claude_code_version`, `uuid` are present in the fixture and dropped. `plugins`, `plugin_errors`, `mcp_server_errors`, `capabilities` are not modelled. |
| `system` / `compact_boundary` | boundary marker | Emitted when history was compacted. | **Missing.** `translate()` returns `null` for any non-`init` system subtype. |
| `system` / `api_retry` | `attempt`, `max_retries`, `retry_delay_ms`, `error_status`, `error`, `no_response`, `uuid`, `session_id` | A retryable API failure is about to be retried. Ideal for a "rate limited, retrying in Ns" banner. | **Missing.** Medusa instead string-matches stderr for token-limit text in `process-manager.ts`. |
| `system` / `plugin_install` | `status` (`started`/`installed`/`failed`/`completed`), `name`, `error` | Marketplace plugin install progress before the first turn. | **Missing.** |
| `system` / `permission_denied` | denial details | With `--permission-prompts none`, denials surface as these messages, and the final `result` lists them in `permission_denials`. | **Missing.** |
| `hook_started` / `hook_progress` / `hook_response` | hook name, output | Streamed while a `SessionStart` or `Setup` hook runs, ahead of `system/init`. `--include-hook-events` widens this to hook lifecycle events generally. | **Missing.** |
| `prompt_suggestion` | suggested next prompt | Emitted after each turn when `--prompt-suggestions` is passed. | **Missing.** Would be a cheap win for the Hub's next-action affordance. |
| `stream_event` | `event` (raw Claude API event), `session_id`, `parent_tool_use_id`, `user_message_uuid` | Only with `--include-partial-messages`. Main session only; subagent token deltas are not forwarded. | **Broken.** `StreamParser.translate()` switches on top-level `content_block_delta` / `content_block_start`, which the CLI never emits at top level: they arrive nested under `stream_event.event`. Compounding it, `process-manager.ts` never passes `--include-partial-messages`, so no `stream_event` lines are produced at all. Result: the `delta` and `tool_use_start` branches are dead code in production. |
| `stream_event.event` = `content_block_delta` with `text_delta` | `delta.text` | Token-level text. | Would be handled if unwrapped and enabled. |
| `stream_event.event` = `content_block_delta` with `input_json_delta` | `delta.partial_json` | Streaming tool-input JSON. | **Missing** by design comment ("ignored for now"). |
| `stream_event.event` = `message_delta` | `delta.stop_reason`, `usage.output_tokens`, `context_management.applied_edits` | Per-message stop reason and incremental output tokens. | **Missing.** |
| `assistant` | `message.{id,role,content[],model,stop_reason,usage}`, `session_id`, `parent_tool_use_id` | One message per completed content block. `content[]` carries `text`, `thinking`, and `tool_use` blocks. | **Partial.** Parsed into `assistant_complete`, but `server/src/socket/handler.ts` iterates only `block.type === "text"`. **`tool_use` blocks are silently discarded**, which is why tool cards do not appear. `thinking` blocks are likewise dropped. `message.usage` on assistant messages is not read. |
| `user` | `message.content[]` of `tool_result` blocks, `tool_use_result`, `session_id`, `parent_tool_use_id` | How tool results actually reach the stream. The `ContentBlockToolResult` path in the parser keys off `content_block_start`, which never carries a `tool_result`, so `ParsedToolResult` never fires. |
| `result` / `success` | `result`, `total_cost_usd`, `duration_ms`, `duration_api_ms`, `num_turns`, `session_id`, `usage`, `modelUsage`, `is_error`, `stop_reason`, `permission_denials`, `structured_output` | Final line of the run. | **Partial.** Captures `result`, cost, durations, turns, session, `usage`. Ignores `is_error`, `stop_reason`, `modelUsage`, `permission_denials`, `structured_output`, all of which are in the fixture or documented. |
| `result` / error subtypes | `error_max_turns`, `error_during_execution`, `error_max_budget_usd`, plus an `errors[]` array for worktree-resume refusals | Terminal failure modes. | **Partial.** Any non-`success` subtype collapses to `{success: false, error: ev.error}`; the distinct subtypes and `errors[]` are lost. |
| `usage` object | `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `server_tool_use` | Token accounting on `result` and on `message_delta`. | **Partial.** Four fields modelled in `UsageInfo`; `server_tool_use` and per-model splits are not. |
| `parent_tool_use_id` | on `assistant`, `user`, `stream_event` | `null` for the main conversation; the `Agent` tool-call id for subagent messages, at every nesting depth. `--forward-subagent-text` also forwards subagent text and thinking blocks. | **Missing.** Present in every line of the fixture and referenced nowhere in `server/src` or `client/src`. No subagent attribution is possible today. |
| `structured_output` on `result` | schema-conforming JSON | Populated when `--json-schema '<schema>'` is passed. Turns a turn into a typed API call. | **Missing.** Useful for Medusa's `[HUB-POST:]` and `[BOT-TASK:]` markers, which are currently scraped out of free text by `hub-detector`. |
| Control protocol (`--input-format stream-json`) | `control_request` / `control_response`, plus `--replay-user-messages` | Bidirectional channel for interrupt and for `canUseTool`-style permission answers, and for multi-turn input without respawning the process. | **Missing.** `process-manager.ts` writes the prompt as a plain argument, spawns a fresh process per turn, and kills it to abort. |

**Net effect.** Medusa's parser was written against an idealized flat event shape. Against the real CLI it correctly handles exactly two things: `system/init` and `result`. Everything the user sees in chat comes from the `assistant` path, text blocks only. That single mismatch explains the missing streaming, the empty tool cards, and the invisible subagents at once.

**Flags Medusa should be passing and is not.** `process-manager.ts` currently builds `-p --output-format stream-json --verbose [--session-id|--resume] [--dangerously-skip-permissions] [--system-prompt] [--model]`. Missing and immediately useful: `--include-partial-messages` (streaming), `--forward-subagent-text` (subagent transcripts), `--include-hook-events`, `--permission-mode`, `--allowedTools` / `--disallowedTools`, `--permission-prompts none` for unattended poll runs, `--max-turns` and `--max-budget-usd` as runaway guards on autonomous bots, `--add-dir`, `--mcp-config`, `--agents`, `--fork-session`, `--json-schema` for the Hub markers, and `--append-system-prompt` instead of `--system-prompt` where the default Claude Code prompt is still wanted. `--bare` is worth knowing about as the opposite lever: it skips all discovery, which is what Medusa's poll and nudge runs probably want for determinism and cost.

The fixture in `docs/stream-format-example.jsonl` is a useful start but thin: it has no `tool_use` assistant block, no `system/api_retry`, no `compact_boundary`, no error `result`, no `permission_denials`, and no subagent messages. Per Section 9.4 of the plan, capture fixtures for a tool-use turn, a permission denial, a compaction, a subagent run, and an API retry before writing the second engine's parser.

### Recent changelog signals (v2.1.269 to v2.1.272)

Worth tracking because they show where the product is heading, from https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md:

- **Per-command `allowed_domains`.** Bash, PowerShell, and Monitor in auto mode with sandboxing now declare the hosts a command needs, and only those are opened. Network permissions are getting finer, not coarser.
- **Auto-mode subagent hand-back.** A subagent reports back through a dedicated call the safety classifier reviews, rather than after-the-fact review of its last message. Subagent output is treated as untrusted input.
- **Markdown artifacts render as documents**, and a session can watch up to 10 published artifacts for republishes. Artifacts are becoming the default delivery format for finished work.
- **Monitor watches always have a deadline** (30 minutes, 10 in `-p`), and the no-timeout `persistent` option is gone. Relevant to Medusa's poll scheduler, which has no deadline at all.
- **`/output-style [name]` returned** and works over Remote Control and in cloud and headless sessions.
- **Bash edit diffs**: when the Bash tool handles a file edit, the tool result now includes a diff. Another argument for building the diff surface (gap 5).
- **VSCode agent map**: an "N agents" pill opens a map of the session's subagents with per-agent cards, Stop agent, and read-only transcripts. This is the shape gap 6 should aim at.

## 4. Top 10 gaps to close

1. **Parse the real stream shape.** Unwrap `stream_event.event`, handle `type: "user"` tool results, and read `tool_use` blocks out of `assistant` messages in `server/src/socket/handler.ts`. Without this, tool cards are permanently empty. `stream-parser.ts`, `types.ts`, `handler.ts`. **P0**
2. **Turn on token streaming.** Add `--include-partial-messages` in `server/src/claude/process-manager.ts` and route `content_block_delta` through the existing `delta` path so responses stream instead of landing in one block. **P0**
3. **Real permission plumbing.** Replace the `[HUB-POST: APPROVAL NEEDED]` text convention with the CLI's own permission surface: `--permission-mode`, `--allowedTools` rules, a `--permission-prompt-tool` or `--input-format stream-json` control channel, and `permission_denials` from the `result` event. Keep `ApprovalBanner.tsx` as the UI, change what feeds it. Sandboxing (`sandbox.enabled`) belongs in the same pass: Medusa currently runs an autonomous agent with no permission checks and no OS isolation. **P0**
4. **Permission modes as a first-class session field.** Replace the `yoloMode` boolean with `default` / `acceptEdits` / `plan` / `auto` / `bypassPermissions`, switchable mid-session, with a per-session default in settings. This is also the prerequisite for plan mode. **P0**
5. **Diff viewer.** A file-by-file diff pane with line comments is the single biggest missing surface for a coding agent; today a Medusa user cannot see what changed without opening an editor. **P0**
6. **Subagent visibility.** Thread `parent_tool_use_id` through `ParsedEvent` and the socket payloads, add `--forward-subagent-text`, and render nested agent activity as a collapsible group plus a background-tasks pane. **P1**
7. **MCP support.** Surface `mcp_servers` and `mcp_server_errors` from `system/init`, add a `.mcp.json` editor and a status view, and pass `--mcp-config` per session. Medusa already receives this data and throws it away. **P1**
8. **Worktree isolation per session.** Add a worktree toggle on session create backed by `--worktree`, plus `.worktreeinclude` handling and exit cleanup. Concurrent bots currently share one checkout. **P1**
9. **Routines UI over the poll scheduler.** Generalize `poll-scheduler.ts` into user-defined scheduled tasks with name, instructions, folder, model, permission mode, schedule preset, Run now, pause, and run history, and give scheduled runs their own sidebar section. **P1**
10. **Slash commands, hooks, and local skills.** Add `/` expansion in `ChatInput.tsx` over a command registry, a `settings.json` hooks block the server executes, and local `.claude/skills` discovery alongside the existing remote catalog. These three are what make the harness programmable rather than promptable. **P1**

Runner-up, and the reason to do items 1 to 3 first: every one of them is also the contract the second engine must satisfy in Phase 2, so fixing the Claude path now defines the interface for `OpenHarnessEngine` rather than duplicating a broken one.
